01 · Objetivo de aprendizaje

Al terminar esta práctica podrás explicar la diferencia entre autenticación (quién eres) y autorización (qué puedes hacer), seguir una petición protegida por Express y probar respuestas exitosas y denegadas.

La implementación vive en src/auth, src/middlewares, src/services/auth.service.ts y las rutas de src/routes.

02 · Dos conceptos, dos preguntas

JWT (JSON Web Token) es un token firmado que la API entrega después de comprobar las credenciales. En cada solicitud protegida, el cliente lo envía en el encabezado Authorization: Bearer <token>. La firma permite detectar cambios; el contenido del token no está cifrado, así que nunca pongas contraseñas ni datos secretos dentro.

RBAC (Role-Based Access Control) asigna permisos a roles. El middleware comprueba el rol antes de que el controlador ejecute la acción. Tener un token válido no significa tener permiso para todas las rutas.

Idea clave: validar el token responde «¿quién llama?»; autorizar el rol responde «¿puede realizar esta acción?».

04 · El recorrido de una solicitud

1. LoginSe envían correo y contraseña a POST /api/v1/auth/login.
2. VerificaciónLa API compara el hash y comprueba que la cuenta esté activa.
3. TokenSe firma un JWT HS256 con identidad y rol; expira en 15 minutos.
4. PermisoEl middleware valida firma y vencimiento; luego RBAC decide si continúa.

¿Qué aporta cada pieza?

  • bcryptjs compara la contraseña con el hash guardado; la contraseña original no se almacena.
  • authenticate valida el token y pone el usuario autenticado en req.user.
  • authorize(...roles) permite o deniega según el rol incluido en el token.
  • El controlador toma el guardaId desde req.user; el guarda selecciona al instructor destinatario y la API valida que sea un instructor activo.

}

El token lleva solo identidad, correo y rol; nunca contraseña ni hash. El helper también valida que el rol del token sea uno de los tres permitidos.

Paso 3 · Busca al usuario y compara la contraseña

  • src/repositories/user.repository.ts declara el contrato de búsqueda por correo.
  • src/repositories/prisma-user.repository.ts obtiene usuario, rol, estado y passwordHash desde Prisma.
  • src/services/auth.service.ts normaliza el correo, rechaza cuentas inactivas o sin hash y ejecuta bcrypt.compare(password, passwordHash).

Si la validación falla, responde el mismo error de credenciales para no revelar si un correo está registrado. Si funciona, el servicio emite el token y devuelve un perfil sin la contraseña ni el hash.

Paso 4 · Crea el endpoint de login y valida su entrada

El validador src/middlewares/validateAuth.middleware.ts acepta únicamente email y password; comprueba formato, tipos y el máximo de 72 bytes que admite bcrypt. El controlador delega en el servicio.

POST /api/v1/auth/login
Content-Type: application/json

{ "email": "instructor.ti@sena.edu.co", "password": "<contraseña>" }

Registra la ruta en src/routes/auth.routes.ts y monta el router con router.use('/auth', authRoutes) en src/routes/index.ts. El login es público; GET /auth/me sí requiere token.

Paso 5 · Protege rutas con dos middlewares

  • authenticate lee Authorization: Bearer ..., verifica el JWT y guarda al usuario en req.user. Si falta o no es válido, responde 401.
  • authorize(...roles) compara req.user.rol con los roles permitidos. Si el usuario está autenticado pero no autorizado, responde 403.

Paso 6 · Aplica RBAC y evita suplantación

En src/routes/loan.routes.ts, agrega router.use(authenticate) y la autorización por endpoint:

  • POST /loans: solo GUARDA; el guarda queda asociado como creador.
  • GET /loans/search y GET /loans/:id: los tres roles autenticados; guardas e instructores ven solo los suyos.
  • PUT /loans/:id/accept: solo INSTRUCTOR y únicamente si el préstamo está asignado a él.

En el controlador, toma guardaId de req.user.id, nunca del cuerpo. El instructorId del cuerpo señala al destinatario; el servicio verifica que sea un instructor activo. Las consultas quedan limitadas al guarda creador o al instructor asignado, según el rol.

import jwt from 'jsonwebtoken';
import { AuthenticatedUser } from './authenticated-user';
import { isUserRole } from './roles';

const ISSUER = 'controllabs-api';
const AUDIENCE = 'controllabs-client';
const TOKEN_LIFETIME_SECONDS = 900;

const getJwtSecret = (): string => {
  const secret = process.env.JWT_SECRET;
  if (!secret || Buffer.byteLength(secret, 'utf8') < 32) {
    throw new Error('JWT_SECRET debe estar configurado con al menos 32 bytes.');
  }
  return secret;
};

export const createAccessToken = (user: AuthenticatedUser): string =>
  jwt.sign(
    { email: user.email, rol: user.rol },
    getJwtSecret(),
    {
      algorithm: 'HS256',
      audience: AUDIENCE,
      expiresIn: TOKEN_LIFETIME_SECONDS,
      issuer: ISSUER,
      subject: user.id
    }
  );

export const verifyAccessToken = (token: string): AuthenticatedUser | null => {
  const payload = jwt.verify(token, getJwtSecret(), {
    algorithms: ['HS256'],
    audience: AUDIENCE,
    issuer: ISSUER
  });
  if (
    typeof payload === 'string' ||
    typeof payload.sub !== 'string' ||
    typeof payload.email !== 'string' ||
    !isUserRole(payload.rol)
  ) {
    return null;
  }

  return { id: payload.sub, email: payload.email, rol: payload.rol };
};

export { TOKEN_LIFETIME_SECONDS };

Paso B7 · src/services/auth.service.ts — archivo nuevo completo 
import bcrypt from 'bcryptjs';
import { AuthenticatedUser } from '../auth/authenticated-user';
import { createAccessToken, TOKEN_LIFETIME_SECONDS } from '../auth/jwt';
import { DomainError } from '../errors/domain.error';
import { UserRepository } from '../repositories/user.repository';

export class AuthService {
  constructor(private readonly userRepository: UserRepository) {}

  public async login(
    email: string,
    password: string
  ): Promise<{ accessToken: string; expiresIn: number; user: AuthenticatedUser }> {
    const user = await this.userRepository.findByEmail(email.trim().toLowerCase());
    const passwordMatches =
      user?.passwordHash !== null &&
      user?.passwordHash !== undefined &&
      (await bcrypt.compare(password, user.passwordHash));

    if (!user || !user.activo || !passwordMatches) {
      throw new DomainError('UNAUTHORIZED', 'Correo o contraseña incorrectos.');
    }

    const authenticatedUser: AuthenticatedUser = {
      id: user.id,
      email: user.email,
      rol: user.rol
    };
    return {
      accessToken: createAccessToken(authenticatedUser),
      expiresIn: TOKEN_LIFETIME_SECONDS,
      user: authenticatedUser
    };
  }
}

Paso C1 · src/middlewares/validateAuth.middleware.ts — archivo nuevo completo 
import { NextFunction, Request, Response } from 'express';

const isLoginPayload = (
  value: unknown
): value is { email: string; password: string } => {
  if (typeof value !== 'object' || value === null || Array.isArray(value)) {
    return false;
  }
  const payload = value as Record<string, unknown>;
  return (
    Object.keys(payload).every((key) => key === 'email' || key === 'password') &&
    typeof payload.email === 'string' &&
    payload.email.length <= 255 &&
    /^[^\s@]+@[^\s@]+\.[^\s@]+$/.test(payload.email) &&
    typeof payload.password === 'string' &&
    Buffer.byteLength(payload.password, 'utf8') > 0 &&
    Buffer.byteLength(payload.password, 'utf8') <= 72
  );
};

export const validateLoginPayload = (
  req: Request,
  res: Response,
  next: NextFunction
): void => {
  if (!isLoginPayload(req.body)) {
    res.status(400).json({
      success: false,
      code: 'VALIDATION_ERROR',
      error: 'Debes enviar un correo válido y una contraseña de hasta 72 bytes.'
    });
    return;
  }
  next();
};

Paso D1 · src/middlewares/auth.middleware.ts — archivo nuevo completo 
import { NextFunction, Request, Response } from 'express';
import { JsonWebTokenError, NotBeforeError, TokenExpiredError } from 'jsonwebtoken';
import { verifyAccessToken } from '../auth/jwt';
import { UserRole } from '../auth/roles';

export const authenticate = (
  req: Request,
  res: Response,
  next: NextFunction
): void => {
  const authorization = req.header('authorization');
  const bearerToken = /^Bearer\s+([^\s]+)$/i.exec(authorization ?? '');
  if (!bearerToken) {
    res.status(401).json({ success: false, error: 'Se requiere un token Bearer válido.' });
    return;
  }

  try {
    const user = verifyAccessToken(bearerToken[1]);
    if (!user) {
      res.status(401).json({ success: false, error: 'El token no es válido.' });
      return;
    }
    req.user = user;
    next();
  } catch (error) {
    if (
      error instanceof JsonWebTokenError ||
      error instanceof TokenExpiredError ||
      error instanceof NotBeforeError
    ) {
      res.status(401).json({ success: false, error: 'El token no es válido o ha expirado.' });
      return;
    }
    next(error);
  }
};

export const authorize = (...allowedRoles: UserRole[]) => (
  req: Request,
  res: Response,
  next: NextFunction
): void => {
  if (!req.user) {
    res.status(401).json({ success: false, error: 'Debes iniciar sesión para continuar.' });
    return;
  }
  if (!allowedRoles.includes(req.user.rol)) {
    res.status(403).json({ success: false, error: 'No tienes permiso para realizar esta acción.' });
    return;
  }
  next();
};

public async acceptLoan(id: string, instructorId: string): Promise<Loan> {
  await this.getLoanDetail(id, { instructorId });
  const updatedLoan = await this.loanRepository.updateStatus(
    id,
    'PENDIENTE_APROBACION',
    'APROBADO_Y_FIRMADO'
  );
  if (updatedLoan) {
    return updatedLoan;
  }

  const currentLoan = await this.loanRepository.findById(id);
  if (!currentLoan) {
    throw new DomainError('NOT_FOUND', `No existe un préstamo con identificador ${id}.`);
  }
  if (currentLoan.instructorId !== instructorId) {
    throw new DomainError('FORBIDDEN', 'No tienes permiso para aceptar este préstamo.');
  }
  throw new DomainError('CONFLICT', 'El préstamo ya fue aceptado y no puede aceptarse nuevamente.');
}

09 · Crear hash para una cuenta existente

La base semilla trae usuarios, pero no contraseñas. Un administrador debe asignar un hash a cada cuenta que vaya a probar. Genera hashes localmente; el siguiente ejemplo de PowerShell solicita la contraseña sin mostrarla y solo imprime el hash:

$securePassword = Read-Host "Contraseña temporal" -AsSecureString
$pointer = [IntPtr]::Zero
try {
  $pointer = [Runtime.InteropServices.Marshal]::SecureStringToBSTR($securePassword)
  $env:INITIAL_PASSWORD = [Runtime.InteropServices.Marshal]::PtrToStringBSTR($pointer)
  node -e "require('bcryptjs').hash(process.env.INITIAL_PASSWORD, 12).then(console.log)"
} finally {
  Remove-Item Env:INITIAL_PASSWORD -ErrorAction SilentlyContinue
  if ($pointer -ne [IntPtr]::Zero) {
    [Runtime.InteropServices.Marshal]::ZeroFreeBSTR($pointer)
  }
}

Copia el hash resultante —no la contraseña— y asígnalo a un usuario específico mediante una herramienta administrativa, por ejemplo:

UPDATE users
SET password_hash = '<HASH_BCRYPT_GENERADO>'
WHERE email = 'instructor.ti@sena.edu.co' AND activo = true;

Confirma que la actualización afectó exactamente una cuenta. Repite el proceso con un usuario GUARDA y uno ADMIN para probar la matriz. No publiques el hash ni una contraseña de aprendiz en Git.

10 · Configurar el secreto, arrancar y probar

1. Prepara la clave JWT

El secreto debe ser aleatorio y mantenerse privado. Este comando genera 32 bytes aleatorios codificados para el entorno:

$env:JWT_SECRET = (node -e "console.log(require('node:crypto').randomBytes(32).toString('base64url'))")

Ejecuta el comando y luego arranca la API en la misma terminal de PowerShell; así el proceso hereda la variable:

npm run db:generate
npm run build
npm run dev

Espera el mensaje de servidor iniciado. En otra terminal, ejecuta las peticiones de abajo. En despliegues permanentes configura JWT_SECRET en el gestor de secretos del entorno, no en el repositorio.

2. Inicia sesión como guarda

$guardBody = @{ email = 'guarda.seguridad@sena.edu.co'; password = '<contraseña del guarda>' } | ConvertTo-Json
$guardLogin = Invoke-RestMethod -Uri 'http://localhost:5000/api/v1/auth/login' -Method Post -ContentType 'application/json' -Body $guardBody
$guardToken = $guardLogin.data.accessToken
$guardHeaders = @{ Authorization = "Bearer $guardToken" }
Invoke-RestMethod -Uri 'http://localhost:5000/api/v1/auth/me' -Headers $guardHeaders

3. El guarda genera un préstamo para un instructor

Usa UUID reales de una sala y de un usuario con rol INSTRUCTOR. El backend asigna guardaId desde el token del guarda:

$loanBody = @{
  roomId = '<UUID_REAL_DE_SALA>'
  instructorId = '<UUID_REAL_DE_INSTRUCTOR>'
  numeroPc = 12
} | ConvertTo-Json
$createdLoan = Invoke-RestMethod -Uri 'http://localhost:5000/api/v1/loans' -Method Post -Headers $guardHeaders -ContentType 'application/json' -Body $loanBody
$createdLoan.data

El guarda puede listar sus propios préstamos:

Invoke-RestMethod -Uri 'http://localhost:5000/api/v1/loans/search' -Headers $guardHeaders

4. Inicia sesión como el instructor asignado y acepta

$instructorBody = @{ email = 'instructor.ti@sena.edu.co'; password = '<contraseña del instructor>' } | ConvertTo-Json
$instructorLogin = Invoke-RestMethod -Uri 'http://localhost:5000/api/v1/auth/login' -Method Post -ContentType 'application/json' -Body $instructorBody
$instructorToken = $instructorLogin.data.accessToken
$instructorHeaders = @{ Authorization = "Bearer $instructorToken" }
$loanId = $createdLoan.data.id
Invoke-RestMethod -Uri "http://localhost:5000/api/v1/loans/$loanId/accept" -Method Put -Headers $instructorHeaders

La aceptación solo funciona si instructorId del préstamo coincide con el usuario del token. El instructor puede listar únicamente los préstamos asignados a él.

5. Verifica los casos de acceso denegado

La implementación está completa cuando puedes marcar todo esto

  • Instalaste jsonwebtoken, bcryptjs y los tipos necesarios.
  • La columna password_hash existe y las cuentas de prueba tienen hashes bcrypt.
  • npm run db:generate y npm run build finalizan correctamente.

12 · Prueba final en Postman: autorización Bearer Token

En Postman crea un Environment llamado ControlLabs local con estas variables. Sustituye los UUID por datos que existan en tu base:

baseUrl        http://localhost:5000
guardToken
instructorToken
loanId
roomId         <UUID real de una sala>
instructorId   <UUID real del instructor que inicia sesión>

Petición 1 · Login del guarda

  1. Método POST; URL {{baseUrl}}/api/v1/auth/login.
  2. En Authorization, selecciona No Auth porque login es la ruta pública.
  3. En Body → raw → JSON, envía:
{
  "email": "guarda.seguridad@sena.edu.co",
  "password": "<contraseña provisionada para el guarda>"
}

Debe responder 200 OK. En Scripts → Post-response (o Tests, según la versión de Postman), guarda el token:

pm.environment.set('guardToken', pm.response.json().data.accessToken);

Petición 2 · El guarda crea el préstamo

  1. Método POST; URL {{baseUrl}}/api/v1/loans.
  2. En Authorization → Type, selecciona Bearer Token. En el campo Token escribe {{guardToken}}. Postman enviará Authorization: Bearer <token>.
  3. En Body → raw → JSON, envía:
{
  "roomId": "{{roomId}}",
  "instructorId": "{{instructorId}}",
  "numeroPc": 12
}

No envíes guardaId: la API lo obtiene del JWT. Debe responder 201 Created. Guarda el ID devuelto con este script:

pm.environment.set('loanId', pm.response.json().data.id);

Petición 3 · Login del instructor asignado

  1. Método POST; URL {{baseUrl}}/api/v1/auth/login; Authorization → No Auth.
  2. Envía el correo y la contraseña de la cuenta cuyo UUID usaste como instructorId.
  3. Guarda el token en Scripts → Post-response:
pm.environment.set('instructorToken', pm.response.json().data.accessToken);

Petición 4 · El instructor acepta ese préstamo

  1. Método PUT; URL {{baseUrl}}/api/v1/loans/{{loanId}}/accept.
  2. En Authorization → Type, selecciona Bearer Token y escribe {{instructorToken}}.
  3. No necesitas cuerpo. Envía la petición: el instructor destinatario debe obtener 200 OK y el estado APROBADO_Y_FIRMADO.

Pruebas negativas para confirmar los permisos

  • Repite la petición 4 con {{guardToken}}: debe responder 403 Forbidden; el guarda no acepta.
  • Usa un token de otro instructor para aceptar el mismo loanId: debe responder 403 Forbidden.
  • Quita el Bearer Token de POST /loans: debe responder 401 Unauthorized.
Recorrido correcto: login como guarda → Bearer Token del guarda → crear el préstamo indicando al instructor → login como ese instructor → Bearer Token del instructor → aceptar el ID creado.
